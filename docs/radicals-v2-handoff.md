## 2. V2 候選方向（**均需先確認產品範圍**）

| 候選 | 教學目標與例子 | 主要擴充需求 | 狀態 |
| --- | --- | --- | --- |
| A. 分母有理化與含根式分數 | `1/√2 = √2/2`、`3/√5 = 3√5/5` | 分數係數或分子／分母的精確表示、判定及輸入／顯示 | 候選，未決定優先度 |
| B. 異類方根的加減與多項結果 | `√2 + √3` 不可合併；`√8 + √3 = 2√2 + √3` | 多項根式正規化（同類項合併、排序、正負號）、複合輸入與顯示 | 候選，未決定優先度 |
| C. 進階複合運算／選用提示 | 例如較長的多項化簡與合併 | 題目長度及工作記憶負擔控制、可選提示或進階模式 | **不預設納入** V2 常規題庫 |
| D. 依試用調整難度與訂正 | 依學生實際卡關題型改善引導 | 記錄樣本、調整模板與提示；必要時細分錯因 | 可優先獨立改善，不必等 V2 |

上述 A、B 是先前留待後續版本的主要數學範圍；C、D 為可能的教學與體驗改善。**不要同時把所有候選視為開發指令。** V1 已決定「異類方根不可合併」在提示中教學、不新增判斷題；V2 是否加入能否合併的獨立判斷題也尚未決定。

## 3. 現有技術限制與接手須知

1. **答案語法**：現有 `radical` 答案型別只接受整數或單項 `c√d`；一欄最多一個 `√`，不接受分數、小數、`+`、多個根號或運算式。**不能只擴充出題器，就宣稱支援 A／B。**
2. **數學正確性**：V2 若支援分數係數，須明訂精確有理數表示、約分與最簡形式；若支援多項根式，須明訂合併同類項、排列順序、零項、負號及等值但未最簡的判定。不以 `parseFloat` 或容差取代精確運算。資料結構（例如分子／分母、term 陣列）**尚未定案**，先做規格與測試。
3. **UI**：V1 鍵盤會按 `radical`、`integer`、`legacy` 欄位切換輔助鍵；新語法涉及分數、運算符、多根號及根號頂線的作用範圍，須重新驗證單欄輸入是否仍適合，勿直接堆疊按鍵。需保留無障礙、觸控尺寸、320～430px、實體鍵盤與安全轉義。
4. **題庫／教學**：既有根式 V1 固定配額與去重，`radicals` 關卡 ID 不應改動；新的子類與提示要避免三項以上高負擔長算式直接進入常規題庫。分母有理化與異類多項結果各自需要新的心算策略及訂正設計。
5. **回歸保護**：保留原五關、V1 根式題庫、星星、非法輸入首次資格、計時器、實際引導題數與 TODO；不要順手處理 BUG-05～07。現階段仍以 `index.html` 為主要程式入口，相關測試在 `tests/`，不要無故大改架構。

## 4. 下次啟動 V2 前需先由產品端決定

- **範圍優先序**：A 分母有理化、B 異類方根多項結果，還是先做 D 難度／教學調整？建議先選一個最小可驗收的主題。
- **答案輸入形式**：是否維持單欄？分式如何鍵入？多項根式項次交換是否視為正確？哪些非最簡表達要扣首次星星？需在 UI 實作前統一定義。
- **題目難度與分布**：是否保留 V1 的 10／20／30、基礎／中等／挑戰模式？哪些複合算式只放進進階選用模式？以實際學生試作決定，避免只由生成器自評。
- **提示策略**：維持答錯後精簡訂正，或另提供主動提示？主動提示會否影響首次星星，必須先決定。

## 5. 建議開發順序與驗收關卡

1. **需求決策**：選定 V2 的最小範圍，寫清可接受與不接受的答案例子、難度與不做事項。
2. **精確核心與測試**：先建立可組合、可化簡的數學表示及獨立驗算；釐清最簡形式與等值結果。舊 V1 介面與原五關不得被破壞。
3. **輸入與顯示**：以實際手機操作驗證新格式；測試鍵盤、退格、括號或根號範圍、特殊符號與 HTML 安全。
4. **正式生成器與訂正**：配額、去重、可重現種子、題面與中間值驗算；保留「結構優先」的心算品質控制。
5. **雙重驗收**：`npm test` 全套回歸與新題型獨立 oracle 驗算；另輸出多組真實題目人工審查，安排學生／手機試作。測試全綠不等於適合心算。

建議分為數學核心、輸入 UI、題庫整合等可獨立審查 PR，降低單一 `index.html` 的修改衝突；**不要在尚未確認 V2 規格前直接開始實作**。
